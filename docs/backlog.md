# 未実装と今後の検討事項

未実装の機能と、実装済みの機能の前提として残っている制約。  
実装済みの機能の方針は [decisions.md](decisions.md) に置く。  
ここには、未実装のものの今の扱いと理由、手を付けるときの入口を書く。

## ⏳ 後回しにしているもの

### 端末の印刷

Bluetooth のラインプリンタ (ESC/POS) での印刷。

今の扱い:

- レシート (T-22) と精算レポート (T-52) の [印刷] は、押すと「印刷は未実装です」と表示する
- 控えは、管理画面の PDF (レシートの控え・精算レポート・受注票) か、端末の共有 (画像) で渡す

作るとき:

- 32 桁の文字列 (`ReceiptTextBuilder`、`ShiftReportTextBuilder`) をプリンタに送る。  
  OS の印刷の `PrintManager` は使わない
- 前受金の預り証 (受注票) も、端末で出せるようにする

### クラッシュの収集

今の扱い:

- アプリを落とした例外は端末の中に記録し、次の起動で OS のダイアログで出す (`CrashReport`)
- サーバや外部のサービスには送らない

作るとき:

- 収集のサービスを選ぶ
- 選んだサービスを、`MauiProgram` の起動の設定で `CrashReport` と並べて初期化する
- `CrashReport.Crashed` を購読して送る

### 帳票 PDF の 2 ページ目以降

今の扱い:

- 帳票 PDF は 1 ページだけで、入りきらない行は出ない
- OysterReport は 1 シートを 1 ページで描き、改ページに対応していない
- 普段の量でも切れる。  
  欠けるところは次の表のとおり

| 帳票 | 欠けるところ |
| --- | --- |
| 売上日報 | 時間帯とシフトの多い日に、シフトの行 |
| レシートの控え | 明細の多い会計で、末尾の「控え (再発行)」(さらに多いと合計と支払も) |
| 受注票、発注書 | 明細が多いと、明細の後半とその後ろの前受金や備考 |
| 精算レポート | 部門と金種が多いと、後ろの欄 |

作るとき:

- 帳票ごとに、1 ページに入る行数を決める
- テンプレートのシートを複製して (`CopySheet`)、あふれた行を次のページに続ける
- 表題と表の見出しは各ページに出し、合計と支払は最後のページに置く
- 1 ページの行数はコードで持つので、テンプレートの行の高さや並びを変えたら合わせ直す

## 🚫 作らないと決めたもの

| 項目 | 理由 |
| --- | --- |
| 取引の一括送信 (`POST /transactions/batch`) | 端末は会計ごとに 1 件ずつ送り、未送信が溜まるのはオフラインの後だけ。サーバの登録は 1 件ずつのトランザクションなので、一括にして減るのは往復だけ |
| 端末向けの通知 (SignalR のハブ) | 端末は、書き込みの直後と 5 分ごとの差分同期で、マスタと在庫に追い付く。登録の解除は、次のリクエストの 401 で知る |
| 外部向け Webhook と他システムとの連携 (発注の送信、EDI など) | サーバと端末の中で完結させる。発注書は PDF を人が送る |
| 管理画面の MFA / パスキー | 管理画面のログインは、アカウントとパスワードだけにする |
| 在庫から発注数を提案する機能 (発注点) | 商品に発注点や仕入先の列を持たない |

## 🔍 今後の検討事項

実装の前提や制約として分かっていて、必要になったら見直すもの。

### 運用の前提

- サーバは 1 台を前提にしている (SQLite の 1 ファイル、管理画面の自動更新はプロセス内の通知)。  
  複数台にするときは、DB と、サーバ間で変更を配信する仕組みを見直す ([D-37](decisions.md#d-37-管理画面の自動更新はプロセス内の通知で行う))
- 精算は、集計を読んでから確定するまでの間に届いた取引・取消・入出金・前受金を、確定値に含めない
  - 取引と入出金の登録も、シフトが開設中であることを書き込みの条件にしていない。  
    1 つのシフトへの書き込みは、その端末が未送信を発生順に送る
  - 同じシフトへの書き込みと精算が重なる運用なら、集計と確定を 1 文の更新にまとめる。  
    登録にも、シフトが開設中であることを条件に足す
- 日次締めは、集計を読んでから確定するまでの間に届いた取引を、日計に含めない
  - 締めの印 (`HasLateTransactions`) も立てない。  
    取引は、未締めの日として書かれる
  - 起きるのは、締めが数えていないシフトの取引が、締めと重なったとき。  
    締めが数えていないのは、前日の営業日から続いてその日の取引が未送信のシフトや、締めの集計の後に開設したシフト。  
    締めは、その営業日の取引を含むシフトの精算を待つ
  - 締めと取引が重なる運用なら、締めの登録を、集計を読んだときから取引が変わっていないことを条件にする

### 取引の検証

- 会計の支払の種別 (`kind`) は、端末が送った値で検証している。  
  支払方法のマスタの種別とは照らし合わせていない
- 取引の登録は、取消済みの取引 (`status = Voided` と取消の情報) も受け付ける。  
  オフラインで取り消した取引を、まとめて送るための形
  - この形は取消の規則 (承認・シフト・締め) を通らず、在庫・ポイント・端末のレシート連番も動かさない
  - 端末は取消を `POST /transactions/{id}/void` で送っていて、この形を使わない。  
    使わないままなら、登録では受け付けないようにする
- シリアル番号が要る商品でも、サーバは明細のシリアル番号の有無を確認しない (端末は入れるまで会計に進めない)
- 在庫がマイナスになる販売の警告 (`INVENTORY_NEGATIVE`) は、コードを定義しているが付けていない。  
  在庫が負の商品は、ダッシュボードの要確認に出す

### 集計と照合

- 非正規化した値 (シフトの集計列、会員のポイント残高、現在庫) を、履歴から再計算して照合する機能はない。  
  ダッシュボードは、在庫とポイント残高が負のものを要確認に出す

### 同期と端末

- マスタの差分同期には、商品が多いときに `products` を省いて、端末に分けて取らせる形がある (`productsTruncated`)。  
  この形には端末だけが対応していて、サーバは常に全件を返す
- 端末を入れ直すと、それより前にその端末で記録した取引・入出金・前受金は、端末の集計に残らない。  
  精算レポートは、未送信がなくオンラインなら、サーバの集計を使う
- 端末のローカル DB の取引は、消さずに溜まる (取引履歴と返品の元取引に使う)。  
  送信済みの Outbox は 7 日で消す
- 要確認の送信を破棄しても、端末に書いた記録はそのまま残る
  - 残るのは、取引と取消、元の取引の返品済みの数量、自店の在庫の増減、シフトと入出金など
  - 破棄した取引は未送信がなくなるので、取引履歴では送信済に見える。  
    端末で計算する集計にも入る
  - 在庫は、その商品の在庫がサーバで次に動いて、差分同期で届くまで残る
  - 直すときは、破棄で種類ごとに端末の記録を取り消すか、サーバの最新で付け直す
- 端末の受注一覧には前受金を出していない (受注詳細には出す)

### 受注と発注

- 前受金は一部を返せない (全額を、受け取った方法で返す)。  
  受注の変更で金額が前受金を下回っても、変更は止めない。  
  会計のときに、前受金を返してから会計する ([D-14](decisions.md#d-14-前受金はシフトで受け取り会計で全額を充てる))
- 発注と入荷予定は 1 対 1 にしている (分納や欠品は、入荷予定の受領数と予定の差で残す)

### 帳票

- 帳票 PDF の欄に入りきらない長い名前や住所 (商品名、会社名、店舗名、仕入先名、お客様名、住所など) は切れる
  - 右寄せは、欄の幅で頭が切れる
  - 中央寄せは、両側が切れる
  - 左寄せは、値も罫線もない右の欄まではみ出してから、末尾が切れる
- OysterReport は縮小に対応していない。  
  折り返しは空白と改行の位置だけで、行の高さも変えない (空白のない日本語は折り返さない)
- 直すときは、次のどれかにする
  - 組み立てで、欄ごとの字数に合わせて末尾を「…」にする
  - ライブラリで、縮小に対応する
  - ライブラリで、文字ごとの折り返しと行の高さの調整に対応する
