## 🛒 1. 機能

### D-01. 家電・カメラ・ホームセンターの物販 POS にする

- 業種は家電・カメラ・ホームセンターの物販にする。  
  家電店の業務として、ポイント、シリアル番号、配送、取り寄せ・取り置きを扱う
- 端末 (スマートフォンのレジアプリ) で会計し、サーバが API と本部の管理画面を持つ
- 決済端末や決済ゲートウェイとは連携しない
  - 現金: 釣銭の計算まで
  - カード・QR・電子マネーなど: 支払方法として金額を記録するだけ
- 税は日本の消費税 (標準 10%、軽減 8%、非課税) にする。  
  商品ごとに内税・外税を持ち、税率ごとに集計する (インボイス対応のレシート)
- 端末はネットワークが切れても販売を続ける ([D-34](#d-34-端末はオフラインでも販売を続ける))
- 飲食の要素 (モディファイア、テーブル、伝票の分割) と、色・サイズの親子商品は扱わない。  
  家電は色違いでも JAN が別なので、1 商品 = 1 JAN で足りる
- テナントは 1 つ (1 社・複数店舗・複数端末) にし、店舗を最上位の組織にする。  
  自社チェーンの POS なので、テナントの境界は持たない
- 画面の文言は端末・管理画面とも日本語だけにし、多言語のリソースは持たない
- 端末の起動時に OS のダイアログで出すメッセージ (前回の異常終了、ローカル DB を開けない) は、例外として英語のままにする。  
  テンプレートと同じにする共通の部品の文言を変えない

### D-02. 取引は会計を終えてから 1 回で送る

- 端末で会計を終えてから、明細・値引・税・支払を `POST /transactions` で 1 回で送る。  
  サーバは会計の途中の状態を持たない
- 返品も取引として同じ API で送る ([D-05](#d-05-返品は元の取引に紐付けた返品取引にする))。  
  取消は `POST /transactions/{id}/void` で行う
- 会計の途中の保留は端末だけで持つ
- 会計の前の約束 (取り寄せ・取り置き) は、受注として別に持つ ([D-13](#d-13-受注は会計前の約束として持ち会計で完了にする))
- 店頭で成立した取引は次の場合も受理し、警告をレスポンスの `warnings[]` で返す
  - 販売をやめた商品
  - ポイント残高のマイナス
  - 締めた営業日の取引
- レジで会計が終わる物販なので、完了した取引を送るだけの形がいちばん単純になる。  
  オフラインとも相性がよい

### D-03. 金額は端末が計算し、サーバが検証する

- 小計・値引・税・ポイント・合計は、端末が `Pos.Domain` で計算して送る
- サーバは同じコードで再計算し、一致しなければ 422 (`CALCULATION_MISMATCH`) で拒否する。  
  レスポンスには正しい値の `expected` を付ける
- オフラインでも会計でき、計算のコードは 1 つで済む
- 税は税率ごとに明細を合計してから計算し、端数も税率ごとに処理する。  
  インボイスの税率ごとの区分記載と一致する
- 取引値引は、明細へ按分 (最大剰余法) してから税を計算する
- `POST /transactions/calculate` は、登録せずに計算の結果だけを返す
- 計算の仕様は [api-design.md §4](api-design.md#-4-金額税ポイント計算仕様-共有ライブラリ)

### D-04. ポイントは商品ごとの還元率で付け、1 円として使う

- 付与は、商品の還元率 (`pointRate`) で明細ごとに計算する。  
  付与の基準 (税込・税抜) と端数処理は会社設定にする
- 利用は支払方法の 1 つ (`Kind = Points`) として、1 pt = 1 円で充てる。  
  充てた分にはポイントを付けない。  
  支払方法として扱うので、精算とレポートにそのまま載る
- ポイントを付ける・使う取引には会員が要る
- 残高と履歴 (付与、利用、返品による取消と返還、取引の取消、手動の調整) はサーバが持つ
- 計算式は [api-design.md §4.4](api-design.md#44-ポイント)

### D-05. 返品は元の取引に紐付けた返品取引にする

- 返品は `type = Return` の取引にし、`originalTransactionId` で元の販売に紐付ける。  
  端末で完結させ、販売と同じ経路で送る
- 返品は明細単位で、元の明細の残りの数量までにする
- 返品の金額は元の取引から計算し、ポイントと在庫を戻す
- 返金の方法は、元の取引で使った支払方法を先頭に出して選ぶ。  
  ポイントで払った分はポイントに戻し、前受金は返金に使わない
- 交換は返品取引と販売取引の 2 件で表す
- 取消 (`void`) は、その取引のシフトが開設中の間だけ行う
- 締めた営業日の取引と、返品のある販売は取り消さず、返品で対応する
- 返品のある販売の取消は、次のように止める
  - 端末は、自分で記録した返品で取消を止める
  - オンラインなら、販売の取消の前にサーバの最新で他の端末の返品を確認する。  
    その販売の返品に未送信があるときは、サーバの状態が古いので確認しない
  - 確認せずに取り消した販売に他の端末の返品があれば、サーバが拒否して未送信の要確認に出る
- 取消は、在庫とポイントを逆向きの履歴で戻す
- 返品の取消は、元の明細の返品済みの数量を戻す
- 同時に通る操作は、1 文の更新の条件で守る
  - 取消と同時の返品・精算・締め: 取消の更新の条件 (シフトが開設中、締めていない、販売なら完了した返品がない)
  - 返品と同時の元の取引の取消: 返品済みの数量を足す更新の条件 (元の取引が完了)
- 返品の計算は [api-design.md §4.5](api-design.md#45-返品)

### D-06. 値引とレジ係の取消は店長以上が承認する

- 取引の担当は、その店舗か本部の有効なスタッフにする (違えば 422 `STAFF_INVALID`)
- 値引は明細値引と取引値引にする。  
  定義済みの値引と、任意の額・率 (理由付き) を使える
- 承認が必要な値引とレジ係の取消には、店長以上の承認者が要る (なければ 422 `APPROVAL_REQUIRED`)
- 端末は承認者を選び、その PIN で本人を確認する
- 担当と承認者の検証は、認証を無効にしても残す

### D-07. シリアル番号は明細に持ち、会計の前に入力を求める

- 商品に「シリアル要」(`requiresSerial`) を持ち、取引の明細にシリアル番号 (`serialNumbers[]`) を持つ
- 端末は明細の編集でシリアル番号を入力する。  
  1 つの明細に同じ番号は重ねられない
- シリアル要の商品は、入力するまで会計に進めない。  
  案内のあとに、その明細の編集を開く
- サーバは必須を検証せず、受け取って保存する。  
  1 つの明細の中で同じ番号が重なるときと、番号に `null` があるときは 400 にする
- 取引はシリアル番号で検索できる (管理画面の取引一覧、端末の取引履歴)。  
  端末はオンラインで、全店の送信済みの取引から検索する
- レシートと取引の詳細にシリアル番号を出す

### D-08. 配送は取引に配送先を付けるだけにする

- 取引に配送先・希望日・時間帯 (`delivery`) を任意で持ち、レシートに配送先を出す
- 配送料・延長保証・設置工事は、サービスの商品 (`Kind = Service`) の明細にする
- 配送の手配と進捗は扱わない。  
  店のレジとしては、レシートに配送先を出せれば足りる

### D-09. レシート番号は端末が採番する

- レシート番号は、端末が `{店舗コード}-{端末番号:00}-{連番:000000}` で採番する。  
  オフラインでも番号が決まり、レシートを出せる
- サーバは重複を 422 (`DUPLICATE_RECEIPT_NO`) で拒否し、端末ごとの最終連番 (`lastReceiptSeq`) を持つ
- 端末は、連番がサーバの最終連番より小さければ合わせる。  
  入れ直した端末でも番号が重ならない

### D-10. 会員はサーバが持ち、端末はオンラインで扱う

- 会員 (顧客) とポイントの残高・履歴はサーバだけが持ち、端末には同期しない
- 端末は次の操作を、どれもオンラインで行う
  - 会員番号・電話番号 (スキャンか電卓) と名前で会員を検索し、取引に付ける
  - 会員の登録・編集
  - 会員の照会 (ポイント履歴、購入履歴)
- ポイントの手動の調整と会員の削除は、管理画面で行う
- 配送先には会員の住所をコピーできる

### D-11. シフトは端末ごとに開き、精算で確定する

- シフトは端末ごとに準備金で開設し、開設中のシフトは端末に 1 つだけにする
- 取引・入出金 (入金、出金、ドロワを開ける)・前受金は、その端末の開設中のシフトに記録する
- 予想現金は、準備金 + 現金売上 − 現金返金 + 入金 − 出金 + 現金の前受金の受取 − 返金にする
- 精算で、実査額 (金種別にも入力できる) と過不足を記録する。  
  現金と件数・金額の集計は、シフトの確定値として持つ。  
  精算したシフトには書き込めない
- 端末の精算レポートに出す集計
  - 未送信がなくオンライン: サーバの集計
  - それ以外: 端末の集計
- 端末を入れ直したときは、サーバに開設中のシフトが残っていれば引き継ぐ
- 細部は [api-design.md §3.13](api-design.md#313-レジ開閉現金管理-shifts)

### D-12. 日次締めは日計を写して持ち、締めた日の取消を止める

- 締めは店舗 × 営業日で行い、締めた時点の日計と内訳 (支払方法別・税率別) のスナップショットを持つ。  
  締めた数字は後から変わらない
- 締めの条件
  - その営業日にシフトがある
  - 関係するシフトがすべて精算済み (その営業日のシフトと、その営業日の取引を含むシフト)
- 締めた営業日の取引は取り消せない (返品で対応する)
- 締めた後に届いた同じ営業日の取引は受理する
  - 警告 (`DAY_ALREADY_CLOSED`) を付ける
  - 締めの記録に、締め後の取引があるという印を付ける
  - 締めを解除して締め直すと、日計に入る
- 取引の検証のあとに先に通った締めにも、取引の登録で印を付ける (警告は付かない)
- 解除は管理者だけが行い、日計と内訳を行ごと消す
- 締めた人は、管理画面のアカウント名で持つ
- 日計の定義は売上の集計と同じにする (取消を除き、返品は負)
- 端末は締めの状態を持たない。  
  締めた日の取消はサーバが拒否し、未送信の要確認に出る
- 管理画面のダッシュボードは、前日までの未締めを要確認に数える
- 細部は [api-design.md §3.14](api-design.md#314-日次締め-dailyclosings)

### D-13. 受注は会計前の約束として持ち、会計で完了にする

- 取り寄せ (入荷を待つ) と取り置き (店頭の在庫を確保する) は受注として持ち、会計は取引 1 回のまま行う。  
  取引の状態と集計の前提 (完了した取引だけを数える) を崩さない
- 状態は入荷待ち (`Ordered`) → 引き渡し待ち (`Arrived`) → 完了 (`Completed`) にする。  
  完了の前ならキャンセル (`Cancelled`) できる。  
  取り置きは、登録した時点で引き渡し待ちにする
- 受注番号は、サーバが `{店舗コード}-O-{連番:000000}` で採番する。  
  受注の登録はオンラインで行う
- 会計のリクエストの `orderId` で受注を指し、同じトランザクションで受注を完了にする。  
  自店の引き渡し待ちでなければ 422 にする。  
  会計を取り消すと、引き渡し待ちに戻す
- 在庫は会計のときに減らし、受注では引き当てない。  
  取り寄せの入荷は受注の状態だけで、在庫の入荷とは別にする
- 受注の変更は、未完了の間だけ管理画面で行う
- 会計の単価は、売価を変更できる商品だけ受注の単価にし、ほかは今の売価にする (取引の検証で売価と一致させるため)
- 端末はホームの受注から、一覧・詳細・会計・入荷・キャンセルを行う。  
  販売のカートを受注にできる。  
  受注から会計したレシートに受注番号を出す
- 細部は [api-design.md §3.15](api-design.md#315-受注-orders)

### D-14. 前受金はシフトで受け取り、会計で全額を充てる

- 前受金 (内金) は受注の記録 (受取と返金) にし、会計では支払方法の前受金 (`Kind = Deposit`) で全額を充てる。  
  売上は会計の 1 回だけになり、取引の仕組みを変えずに済む
- 受取と返金は端末で行い、その端末の開設中のシフトに記録する (オンラインで、自店の受注だけ)。  
  管理画面は見るだけにする
- 前受金の条件
  - 未完了の受注に 1 つ
  - 金額は 1 円以上で、受注の金額まで
  - 支払方法は現金・カード・QR・電子マネー
- 返金は全額を、受け取った方法で返す
- 前受金があるうちは受注をキャンセルできない (返金してからキャンセルする)
- 会計の画面は、前受金を先頭の外せない支払にする
- サーバは、前受金の支払の合計が受注の前受金と同じことを検証する (`PAYMENT_MISMATCH`)
- 会計の合計が前受金より少ないときは、前受金を返金してから会計する
- 会計で受注が完了すると前受金は 0 になり、会計を取り消すと戻る
- 返品の返金には前受金を使わない
- 現金の前受金は、シフトの予想現金に入れて精算で確定する
- 会計で充てた前受金は、現金売上に入れない
- 同時の操作は、受注の状態と前受金の残りを条件にした 1 文の書き込みで守る
- 前受金の支払方法は、有効な行を 1 つだけ持つ (ポイントも同じ)
- 受注票の PDF が前受金の預り証を兼ねる ([D-21](#d-21-帳票はサーバが-pdf-にする))

### D-15. 在庫は変動の履歴と現在庫で持つ

- 在庫の変動 (販売、返品、取消、棚卸、調整、入荷、移動の出荷と受領) をすべて履歴に残し、現在庫はその集計として持つ。  
  棚卸の差や返品を追え、取引による増減と手動の調整を同じ仕組みで扱える
- 在庫を持つ商品 (`trackInventory`) だけ、取引で在庫を動かす
- 販売では在庫の有無を確認しない。  
  マイナスの在庫を許し、管理画面のダッシュボードに表示する
- 棚卸と調整 (調整理由付き) は、端末と管理画面から登録する
- 変動を登録する API は、棚卸と調整だけを受け付ける。  
  ほかの変動は、取引・入荷・移動の操作で作る
- 変動は参照 (取引、入荷、移動) で元の伝票にたどれる
- 端末は自店の在庫を持ち、他店の在庫はオンラインで照会する

### D-16. 入荷と店舗間移動は伝票で持つ

- 入荷は入荷予定 (`Draft`) → 受領 (`Received`) にする。  
  誤って登録した予定はキャンセル (`Cancelled`) できる
- 入荷の受領は届いた数で在庫に入れ、予定との差は明細の受領数に残す。  
  送らなかった明細は予定の数で受け取る
- 店舗間移動は依頼 (`Requested`) → 出荷 (`Shipped`) → 受領 (`Received`) にする。  
  キャンセルは出荷の前だけにする
- 移動の在庫
  - 出荷: 出荷店の在庫を依頼の数だけ減らす
  - 受領: 入荷店の在庫を届いた数だけ増やす
  - 差: 移動の記録に残り、どちらの在庫にも入らない
- 移動番号は出荷店ごとの連番 (`{出荷店コード}-T-{連番:000000}`) にする
- 入荷は仕入先の納品書番号を持つ
- 状態に合わない操作は 422 にする (状態を条件にした更新で遷移させる)
- 入荷予定は管理画面で登録するか、発注から作る ([D-17](#d-17-発注は入荷予定を作りその受領とキャンセルに合わせる))
- 移動の依頼と出荷、仕入先は管理画面で扱う
- 端末は、自店宛の受領待ち (入荷予定と出荷済みの移動) を 1 つの一覧にする。  
  スキャンか JAN の入力で明細を選んで届いた数を入れ、オンラインで受領する
- 細部は [api-design.md §3.16](api-design.md#316-在庫-inventory)

### D-17. 発注は入荷予定を作り、その受領とキャンセルに合わせる

- 発注は下書き (`Draft`) → 発注済み (`Ordered`) → 入荷済み (`Received`) にする。  
  下書きと発注済みはキャンセル (`Cancelled`) できる
- 変更は下書きの間だけにする (バージョンで楽観ロックし、明細は置き換える)
- [発注] で、発注の明細 (数量、仕入単価) をコピーした入荷予定を作る
- 発注と入荷予定は 1 対 1 にする。  
  分納や欠品は、入荷予定の受領数と予定の差で残す
- 発注と入荷予定の状態は、1 つのトランザクションで合わせる
  - 入荷予定を受領する: 発注は入荷済みになる
  - 入荷予定をキャンセルする: 発注もキャンセルになる
  - 発注をキャンセルする: 入荷予定もキャンセルする (受領済みならキャンセルできない)
- 発注番号は店舗ごとの連番 (`{店舗コード}-P-{連番:000000}`) にする
- 発注した人は、管理画面のアカウント名で持つ
- 発注は管理画面だけで行い、注文は発注書の PDF を人が仕入先に送る
- 端末は入荷予定を検品し、納品書番号がないときは発注番号を出す

### D-18. 商品画像は DB に持ち、ハッシュ付きの URL で配る

- 画像は DB の別のテーブル (`ProductImages`) に持つ。  
  バックアップと移行が DB ファイル 1 つで済み、画像と商品の URL を 1 トランザクションで変えられる
- 形式は JPEG と PNG (先頭のバイトで判定) にする。  
  サイズは 2 MB までにし、縮小はしない
- 登録は、本文に画像そのものを送る (`PUT /products/{id}/image`)。  
  multipart にしないので、フォームの偽造の対象にならない
- 商品の `imageUrl` は `/api/v1/products/{id}/image?v={内容のハッシュ}` にする
- 画像を変えると商品のバージョンも進め、差分同期に載せる
- `v` が今の画像と一致する取得は、長くキャッシュできる。  
  ETag で再検証もできる
- 商品の更新と CSV の取込は画像に触れない
- 端末は、画像を表示するときにだけ取得してキャッシュに置く。  
  オフラインではキャッシュだけで出す。  
  画像がなくても販売の操作は止めない

### D-19. 商品の CSV 取込は全行を検証してから反映する

- 1 行でも誤りがあれば何も反映せず、行ごとの結果 (新規、更新、変更なし、エラー) を返す。  
  直してから取り込み直すときに、どこまで入ったかで迷わない
- `dryRun` は検証だけを行う
- 列は CSV の出力 (`GET /products/csv`) と同じにし、出力して編集して戻せるようにする
- 部門と税率はコードで指定する
- コードが一致すれば更新し、なければ登録する。  
  CSV にない商品は削除しない
- 削除済みの商品のコードと JAN は使えない
- 変更のない行は書き込まない (端末の差分同期とバージョンの衝突を増やさない)
- 文字コードは UTF-8 (BOM の有無を問わない) と Shift_JIS を判別する
- 金額の桁区切りを受け付ける
- 管理画面は、ファイルを選ぶとプレビューを出す。  
  誤りがなく変更のある行があるときだけ取り込める
- 反映のときも同じ検証を再実行し、ほかの変更とぶつかれば全体を取り消す

### D-20. 売上は取引から都度集計する

- 売上は取引から都度集計する (取消を除き、返品は負)
- 集計は日別・店舗別・時間帯別・端末別・担当別・支払方法別・税率別・部門別と商品別で出す
- 時間帯は店舗のタイムゾーンで分ける
- 管理画面は集計をグラフと表で見せ、CSV で出す
- 端末は売上照会で、自端末・自店・全店の集計をオンラインで見る (商品別と CSV は管理画面だけ)
- 細部は [api-design.md §3.17](api-design.md#317-レポート-reports)

### D-21. 帳票はサーバが PDF にする

- 帳票は次のとおりで、管理画面から開く (API は管理画面のログインだけ)
  - 精算レポート
  - 売上日報: 締めの有無にかかわらず、取引から集計する
  - レシートの控え: 端末のレシートと同じ項目を出し、末尾に再発行の控えであることと出力日時を入れる
  - 発注書
  - 受注票: お客様に渡す控え。  
    前受金の受取と返金、会計で差し引く額を載せ、預り証を兼ねる
- サーバが Excel のテンプレートに値を差し込んで PDF にする (OysterReport)。  
  フォントは IPAex ゴシックを埋め込む
- レイアウトは Excel で直せ、コードは値の差し込みだけで済む
- 帳票に絵文字は使わない (フォントに依存するため)
- 端末のレシートは、32 桁の文字列を画像にして画面に出す。  
  電子レシートの QR と画像の共有を持つ。  
  サーバの PDF は使わないので、オフラインでも出せる

### D-22. 管理画面はサーバに同居させ、Service を呼ぶ

- 管理画面は、API と同じ ASP.NET Core に同居させた Blazor (Interactive Server) にする。  
  HTTP を経由せずに Core の Service を呼ぶ
- マスタは本部の管理画面で管理し、店舗の端末へ配信する
- 管理画面の機能は、API の管理用の操作と対応させる
- 次の機能は管理画面だけにあり、API を持たない
  - ユーザー
  - 端末のペアリングコードの発行と登録の解除
  - PIN の設定
- 画面は、左のナビゲーションと、一覧のページ + 詳細・編集のダイアログにする
- UI は MudBlazor で作り、一覧はサーバ側でページングする
- 表示の使い分け
  - 見出し: 絵文字
  - 状態: チップ (文言、色、白い単色のアイコン)
  - 件数: バッジ
- 画面の構成でわかる自明な案内は出さない。  
  例は「[保存] で反映します」「URL を確認してください」、操作の手順の説明
- 説明は、画面からわからない業務ルールと操作の結果 (ログアウトする、取消できなくなる) を伝える。  
  句点の要らない短い句にする
- エラーと見つからないページは静的 SSR にする (例外や 404 の再実行で描画するため)
- 画面の一覧と遷移は [screen-design.md §2](screen-design.md#-2-サーバ管理画面-blazor)

### D-23. 端末はメニュー型のホームと F1〜F4 のシェルにする

- 端末は縦持ちのスマートフォンにし、JAN・QR はカメラで読む
- ホームは業務のメニュー (販売を最上段に大きく) にし、各業務からホームへ戻る。  
  機能の一覧性を優先する
- 販売に早く入りたいときは、設定でログインの後に販売の画面を直接開ける
- 画面は、上のタイトル (店舗-端末、担当、未送信のバッジ) と下の F1〜F4 のファンクションキーのシェルに入れる
- F1 は戻る・メニュー、F4 は会計・確定・開設・精算にそろえる
- 遷移の向きは画面の階層で決める。  
  深くなると右から、浅くなると左からスライドする
- シェルとホームは、販売・会計の画面の配色 (紺のヘッダ、白い行、青い金額) にそろえる。  
  角丸のカードは使わない
- 画面の構成と F キーの文言でわかる自明な案内は出さない (「〜してください」、F キーやタップの説明)
- 文言は、異常や注意が要る状態と、操作の結果・事実を伝えるために使う
- 文言は句点の要らない短い句にし、文を重ねない
- 確認は「〜しますか？」にし、取り消しにくい影響を短い句で 1 行だけ添える
- 処理中の表示は IDialog のインジケータだけにする。  
  同期の段階の文言や、「読み込んでいます」のような文言は画面に出さない
- 段階の文言を出せる `IDialog.Loading` は使わない。  
  MAUI のウィンドウのオーバーレイなので、カメラのある画面ではカメラの中に描かれて読み取り枠の下になる
- 会計の支払方法のボタンは、支払方法の短い名前 (`shortName`、なければ `name`) を出す
- 画面の一覧と遷移は [screen-design.md §1](screen-design.md#-1-端末-mauiスマートフォン)

### D-24. 端末の入力は電卓と下端のシートにする

- 数値と番号は電卓で入力し、OS のキーボードに頼らない。  
  対象は数量、金額、枚数、会員番号、電話、郵便番号、商品コード、伝票番号、レシート番号など
- OS のキーボードは、文字 (名前、住所、備考、検索のキーワード、設定) にだけ使う。  
  キーボードは画面の半分を隠し、機種で見た目と挙動も変わる
- 取消・入出金・値引の理由は定型から選ぶ (任意の入力もできる)
- ポップアップ (電卓、明細の編集、値引、理由、金種別の入力) は、画面の下端に寄せたシートにする。  
  シートは重ねて開ける。  
  片手で持ったときに親指が届き、会計の画面のテンキーとも位置がそろう
- 一覧からの選択と確認・案内も、OS のダイアログではなくシートで出す。  
  選択のシートだけ、外側のタップで閉じる
- 画面を離れるときは入力欄のフォーカスを外し、キーボードを次の画面に残さない
- 文字の欄がある画面は、開いたときに欄へ自動でフォーカスしない (キーボードが一覧や入力の続きを隠す)
- 文字の欄が続くフォームは、キーボードの「次へ」で次の文字の欄へ移る。  
  最後の欄の「完了」でキーボードを閉じる

### D-25. 画面は平らな面で状態を示す

- 端末の画面は、灰色の背景の見出しと幅いっぱいの白い面にし、角丸の箱・枠・影を使わない
- 角丸はチップ、アバター、ボタン、下端のシートにだけ使う。  
  同じ箱の繰り返しは読みにくい
- 状態のある一覧 (取引履歴、未送信、保留、棚卸、返品の明細) は、左端のバーと行の背景で状態を示す
- 主な金額は大きく出し、集計は罫線で区切った表にする
- 合計の数え上げのような控えめな動きを付ける。  
  続けて更新する一覧 (販売の明細、棚卸) には付けない
- タップにはリップルを付ける
- 空の一覧とスキャン待ちは、絵文字を中央に出す
- オンラインで取得する画面は、取得中は結果を隠す。  
  取得できないときは、理由を結果に重ねる
- アイコンは背景で使い分ける

| 対象 | 表示 |
| --- | --- |
| 明るい背景で文言に添えるもの (見出し、一覧と表のセル、メニュー、メッセージ、ホームと設定のボタンなど) | 色付きの絵文字 |
| 濃い背景で文言に添えるもの (塗りつぶしのチップ、色付きのボタン、濃い色のバー) | 白い単色のアイコン |
| トースト | 色付きの絵文字 |
| 部品のアイコン (チップとボタンのアイコン、アイコンだけのボタン) | 背景によらず Material Icons のグリフ |
| キーと同じに扱う記号 (シートの ✕ と ✔、テンキーの ⌫、小さな丸ボタンの +、-、✕) | 文字 (部品のアイコンの例外) |
| ラジオボタンの代わりの ◉ と ○ | 文字 (部品のアイコンの例外) |

- 濃い背景の上の絵文字は、背景に溶けて読みにくい
- トーストは OS が描き、背景の明るさが Android のバージョンとテーマで変わる

## 🧩 2. アーキテクチャ

### D-26. サーバ・端末・共有のプロジェクトに分ける

- サーバは次のプロジェクトに分ける
  - `Pos.Server.Core`: 業務の手順とデータアクセス (ASP.NET Core に依存しない)
  - `Pos.Server.Host`: API、管理画面、帳票
  - `Pos.Server.AppHost`: Aspire
- サーバは ASP.NET Core の Minimal API と Blazor (MudBlazor)、SQLite (Smart.Data.Accessor)、Aspire で作る
- 開発時は OpenAPI の文書を出し、Swagger UI と ReDoc で見られる
- 端末は `Pos.Terminal` (MAUI、Android だけ) にする
- 共有は次のプロジェクトに分ける。  
  ドメインロジックと通信データは別の概念なので混ぜない
  - `Pos.Domain`: 列挙型、計算、業務ルール
  - `Pos.Contract`: 通信データ
- `Pos.Domain` は UI・DB・HTTP・`Pos.Contract` に依存させない (テストで検証する)
- 業務ルールの違反はエラーコードと理由で返し、文言はサーバと端末がそれぞれ持つ
- 端末の共通の部品は、MAUI のテンプレート (template-maui) と同じにする。  
  テンプレートの改善を、そのまま取り込めるようにする
  - 対象は添付プロパティ、ナビゲーションのプラグイン、シェル、診断、Android のエントリポイントなど
  - 名前空間と起動時の初期化のほかは変えない
  - テンプレートにしかない機能の行は入れない
  - POS だけの動きと見た目は別のファイルに置く
- 構成の細部は [architecture.md](architecture.md)

### D-27. サーバは Service に手順を集め、SQL は Accessor に置く

- API のエンドポイントと管理画面のページはリクエストの確認・変換と表示だけを持ち、Core の Service を呼ぶ
- Service は業務の手順 (検証、トランザクション、重複とバージョンの判定、変更の通知) を持ち、Accessor と `Pos.Domain` を使う
- SQL は Accessor の外に置かない
- 現在時刻に依存する業務ルール (「今日」「既定の期間」「通信中とみなす条件」など) は Service が持つ。  
  ページとエンドポイントは時計を持たない
- 基盤は ASP.NET Core への依存で置き場所を分ける
  - 依存しないもの: Core
  - 依存するもの (CSV、例外処理、ログ、帳票のフォント): Host

### D-28. 端末は ViewModel から Service と Usecase を呼ぶ

- ViewModel は入力と表示を持ち、Service と Usecase を呼ぶ
  - Service: 単機能の処理
  - Usecase: 通信・DB・完了までをまとめた処理。  
    DB への書き込みとトランザクションは Usecase が行う
- 1 つの業務の画面の間で共有する状態 (カート、返品、棚卸、検品など) は、ナビゲーションの Scope で持つ。  
  参照する画面がなくなると破棄する
- 店舗・端末・担当・シフトは Session に置く
- 画面の遷移は、Smart.Navigation で `ContentView` を差し替える
- ポップアップは `IPopupNavigator` (CommunityToolkit の Popup) で開く
- 操作 (ボタン、F キー、戻る) は、表示中の画面だけが受け付ける。  
  離れていく画面やポップアップの処理が途中で動いたり、遷移が重なったりしないようにする
  - 遷移の間は受け付けない
  - ポップアップを開いている間は、後ろの画面も受け付けない
  - ポップアップも、閉じ始めたら受け付けない
- 通信は `HttpClient` と System.Text.Json (サーバと同じ JSON の設定) で行う。  
  失敗の Problem Details (`errorCode`) を読んで、画面に理由を出す
- 保存先
  - ローカル DB: SQLite (Smart.Data.Accessor)
  - 端末のトークン: SecureStorage
  - 端末の設定: Preferences
- SecureStorage の鍵が壊れてトークンを読めないときは、保存領域を消して未登録として扱う。  
  同じ店舗・番号の端末に登録し直せば、未送信の続きを送る
- Android のバックアップと端末間の転送はしない。  
  端末の識別と、未送信を含むローカル DB を別の端末に移さない
- 起動時にローカル DB を開けないときは、理由を出して終了する。  
  未送信を失わないように、DB は作り直さない
- アプリを落とした未処理の例外は記録し、次の起動で表示する。  
  落ちずに続いた例外は表示しない
- 回線の状態は、MAUI の Essentials (`IConnectivity`) を使わずに Android の通知から受け取る。  
  Essentials は、通知のたびに UI スレッドで状態を再取得する
- バッテリーと無線 LAN の状態も、同じ部品 (`DeviceInformation`) が受け取る (画面では使わない)
- 画像ごとの Glide (MAUI の画像の読み込み) の使い方
  - ボタンのアイコン (Material Icons のグリフ): Glide を通さずに、その場で描く
  - レシート画面の画像 (レシートと QR): Glide を通さずに、SkiaSharp の画像のまま出す
  - 取得した商品画像: Glide で出し、縮小・向きの補正・キャッシュを使う
- Glide を通すと、初回の初期化が UI スレッドを止めて表示が遅れる。  
  商品画像では、初回の初期化で止まっても Release では目立たない
- 表示の色と文言の切り替えは、ViewModel ではなく Converter と Trigger で行う

### D-29. データは SQLite に置き、SQL ファイルで読み書きする

- データアクセスは ORM を使わず、Smart.Data.Accessor の 2-way SQL のファイルで書く
- スキーマと初期データは SQL ファイル (`Schema.sql`、`InitialData.sql`) にし、起動時に実行する。  
  `CREATE TABLE IF NOT EXISTS` なので、何度でも実行できる
- 初期データは、会社設定のない空の DB にだけ入れる
- マイグレーションは持たない。  
  機能は新しいテーブルで足す
- 既存のテーブルに列を足すしかないときは、起動時に列の有無を確認して足す (端末のローカル DB も同じ)
- 更新は `RETURNING` で更新後の行を受け取る
- 編集する行 (マスタ、会員、受注、発注など) は、バージョン (`Version`) で楽観ロックする
- マスタは論理削除にし、差分同期で削除も伝える
- 取引・シフト・入出金・在庫の変動・ポイントの履歴は消さない (取消は状態と逆向きの履歴で表す)
- 一覧の並び順はリソースごとの列挙型で受け、SQL の中で展開する
- 表の定義は [db-design.md](db-design.md)

### D-30. 金額は decimal、ID は GUID v7、日時は UTC にする

- 金額・数量・率は `decimal` にし、SQLite では `NUMERIC` の列にする。  
  数値として保存され、集計がそのまま使える
- 円は整数だけを使い、数量は小数 (切り売り) も持てる
- ID は GUID v7 にし、TEXT (36 文字、大文字のハイフン区切り) で保存する。  
  文字列の順が時系列の順になる
- 日時は UTC にする
  - サーバ: TEXT (`yyyy-MM-dd HH:mm:ss.fffffff`)
  - 端末: INTEGER (ticks)
- 営業日は TEXT (`yyyy-MM-dd`) にする
- 列挙型は TEXT (列挙名) にし、DB を直接見ても読めるようにする
- 真偽値は INTEGER (0 / 1) にする
- 型の対応は [db-design.md §1](db-design.md#-1-前提)

### D-31. API は camelCase の JSON と Problem Details にする

- API は `/api/v1` の下に置き、JSON のプロパティとクエリは camelCase にする
- JSON の値の形式
  - 日時: UTC の `yyyy-MM-ddTHH:mm:ss.fffZ`
  - 日付: `yyyy-MM-dd`
  - 列挙型: 文字列
  - `null`: 省略する
- 通信データは `XxxRequest` と `XxxResponse` と呼び、「DTO」とは呼ばない
- 型の名前
  - 機能名 + 操作名にする (`ShiftOpenRequest`、`InventoryChangesResponse`)
  - 複数の操作で使う型は共有する
  - 一覧は `ListResponse<T>` を継承した `XxxListResponse` にし、要素は `XxxListResponseItem` にする
  - 入れ子の要素は、親の名前 + 要素名にする (`OrderListResponseLine`)
- 一覧は `page` (0 始まり) と `size` で取り、総件数 (`total`) を返す。  
  管理画面の表のページングに総件数が要る
- 並び替えは `sort` と `desc` で指定する
- 差分同期は `updatedSince` で絞り、更新日時と ID の順に返す
- 失敗は Problem Details (`errorCode`、`traceId`) で返す
  - 入力の誤り: 400 (`VALIDATION_ERROR`)。  
    本文の JSON や引数の型が読めないリクエスト、知らない項目・文字列の数値・重複したキー、一覧の `null` の要素も同じ
  - 業務ルールの違反: 422
  - 重複とバージョンの不一致: 409
- 受理したうえでの警告は `warnings[]` で返す
- JSON のコンバータと Problem Details の型は、サーバ・端末・ツールがそれぞれ持つ。  
  `Pos.Contract` には通信データだけを置く
- 細部は [api-design.md §2](api-design.md#-2-共通仕様)

### D-32. 端末発の書き込みは端末が ID を採番する

- 端末が記録する登録は、端末が ID (GUID v7) を採番して送る。  
  対象はシフトの開設、入出金、取引、棚卸・調整、受注、前受金の受取と返金
- 再送の扱い
  - 同じ ID で同じ内容: 登録済みの内容を返す (200)
  - 同じ ID で違う内容: 409 (`DUPLICATE_ID_MISMATCH`)
  - 精算: 同じ実査額の再送を受け付ける
  - 再送が同時に届いたとき: 再取得して、先に登録した方を返す
- オフラインの後の再送は、ID を端末が持つのがいちばん単純に扱える。  
  キーとレスポンスを保存する専用のテーブルも要らない
- サーバだけが作る記録 (取引による在庫の変動、ポイントの履歴など) も GUID v7 にそろえる

### D-33. 端末は Outbox で送り、差分同期で追い付く

- 端末の書き込みは、ローカル DB と Outbox に 1 つのトランザクションで書く
- 同期は Outbox を発生順に 1 件ずつ送る (会計のたびに送る)
- 送信の失敗の扱い
  - 4xx (401 と 429 を除く): 要確認として止め、後続を送らない
  - 5xx と通信できないとき: 間隔を広げて再送する
- サーバは、再送しても通らないリクエストを書く前に検証し、4xx にする
  - 参照先がない
  - リクエストの中の明細などが重なる
  - 一覧に `null` の要素がある
- 5xx にすると、端末が再送し続けて後続が止まる
- 端末の記録の参照先は、行があればよい。  
  記録した後の無効・削除では拒まない
- 例外として、取引と前受金の担当・承認者は [D-06](#d-06-値引とレジ係の取消は店長以上が承認する) のとおり有効なスタッフかを検証する
- 棚卸・調整の一括で参照先がない変動が 1 つでもあれば、どの変動も書かない (1 回の棚卸を分けない)
- 要確認は理由を出し、設定の画面で再送か破棄を選ぶ
- マスタと自店の在庫は、書き込みの直後と定期 (5 分ごと) の差分同期で追い付く
- 商品画像は、表示するときにだけ取得する
- 端末は heartbeat (1 分ごと) を送り、サーバは最終通信から 5 分以内を通信中とみなす
- 同期の流れは [api-design.md §6](api-design.md#-6-端末側の同期フロー)

### D-34. 端末はオフラインでも販売を続ける

| 操作 | 扱い |
| --- | --- |
| シフトの開設、販売、返品、取消、入出金、精算、棚卸・調整 | 端末の DB に記録し、Outbox で後から送る |
| 会員の検索と登録、受注と前受金、入荷と移動の受領、他店の在庫、売上照会、シリアル番号の検索 | サーバの状態が要るので、オンラインで行う |

- マスタと自店の在庫を端末に持ち、計算と検証 (`Pos.Domain`) も端末で行う。  
  マスタは会社設定、店舗、端末、スタッフ、部門、税率、商品、値引、支払方法、調整理由
- スタッフの PIN は同期したハッシュで照合するので、オフラインでもログインできる
- 返品の元にする取引
  - オンライン: サーバの最新 (この端末でまだ送っていない取消と返品を反映する)
  - オフライン: 端末に残る取引 (端末で記録した返品の数量を返品済みに足してある)
- 端末のローカル DB は [db-design.md §6](db-design.md#-6-端末ローカル-db-sqlite-の概要)

### D-35. 認証は管理画面のログイン、端末のトークン、スタッフの PIN にする

- 管理画面はアカウントのログイン (Cookie) にする
- 役割
  - Administrator: すべて
  - Operator: 参照と、取引・在庫・顧客・受注・日次締めの操作
- ログインは静的 SSR のフォームから送り、パスワードは PBKDF2 のハッシュで持つ
- アカウントの削除・無効化・役割やパスワードの変更は、バージョンを進めてログイン中のセッションを無効にする。  
  Cookie はリクエストごとに、開いている回線は 1 分ごとに確認する
- 自分自身は削除・無効化・役割の変更をできない
- アカウントが 1 件もなければ、起動時に設定 (`Auth:InitialName` と `InitialPassword`) の管理者を作る
- 端末は、管理画面で発行したペアリングコード (6 桁、有効期限 10 分、一度だけ) と引き換えにトークンを受け取る (`POST /terminals/pair`)
- 設定の QR は接続先 (`ApiEndPoint`) だけの `Key=Value` の行にし、印刷して使う。  
  毎回変わるコードは QR に入れず、端末の電卓で入れる
- 設定 QR の接続先
  - 端末から届く URL の設定 (`Terminal:ApiEndPoint`) があれば、その URL
  - なければ、管理画面を開いた URL
- 接続先が localhost のままでは端末から届かないので、設定 QR のページにメッセージを出す
- 端末は初期設定の画面のカメラで設定 QR を読み、続けて電卓でコードを入れて登録する
- 登録し直しは、今の登録が使えなくなることと未送信の件数を確認してから行う
- トークンは JWT にせず、リクエストごとに DB で照合する (サーバは SHA-256 だけを持つ)。  
  登録の解除が次のリクエストから効き、署名鍵の運用も要らない
- 同じ端末をペアリングし直すと、古いトークンは失効する。  
  端末ごとに有効なトークンは 1 つにする
- 端末を登録し直すときは、ペアリングが成功してから接続先とトークンを切り替える。  
  失敗したら今の登録に戻す
- ペアリングのリクエストには、今のトークンを付けない (別のサーバへ送らないように)
- ペアリングの間は、今のトークンで通信しない (失効した古いトークンの 401 を、登録の解除と取り違えないように)
- 端末はリクエストが 401 になったら、登録が解除されたことを表示して初期設定に戻る。  
  トークンは捨て、ローカル DB と Outbox は残す。  
  店舗コード・端末番号が同じ端末に登録し直すと、続きを送る
- 店舗コードと端末番号が同じ端末 (新しいサーバの同じレジ) に登録し直したとき
  - 前の登録の未送信 (要確認を含む) を、その店舗・端末のものに書き換えて送る (新しいサーバへ送れるように)
  - 開設を送っていないシフトは、端末の行も移す
  - 開設を送ったシフトに続く未送信は、要確認になる
- 店舗コードか端末番号の違う端末に登録し直したとき
  - 未送信は書き換えない (取引と在庫の変動を別の端末・店舗のものにせず、レシート番号の端末と合わせる)
  - 前の端末の未送信は、サーバが受け付けずに要確認になる (同じサーバの前の端末に登録し直せば送れる)
- スタッフは端末で PIN (4〜6 桁) を照合する
- PIN は `Pos.Domain` の `PinHasher` (PBKDF2) でハッシュにし、端末向けの同期にだけ載せる
- PIN のないスタッフは担当に選べない
- ログインとペアリングは、接続元ごとに 1 分あたりの回数を制限する (`Auth:AttemptsPerMinute`)。  
  短いコードと既定のパスワードの総当たりを防ぐ
- Cookie の `Secure` はリクエストに合わせる (店内の LAN で HTTP のまま動かすこともあるため)
- 開発とデモでは、`Auth:Enabled = false` で認可を素通しにできる (ログイン、ペアリング、トークンの照合は残す)
- 細部は [api-design.md §2.6](api-design.md#26-認証認可)

### D-36. 認可は要件で分け、端末は自店・自端末に限る

| ポリシー | 対象 |
| --- | --- |
| `Api` (管理画面のログインか端末のトークン) | API の既定 |
| `Admin` (管理画面のログイン) | 管理画面だけの操作 (CSV、PDF、日次締め、仕入先、入荷と移動の登録、発注、商品別の売上など) |
| `Administrator` (管理者) | マスタ・会社設定・端末登録の書き込みと、締めの解除 |

- ポリシーはスキームではなく要件 (アカウントの役割、端末のクレーム) で分ける。  
  ASP.NET Core はポリシーを重ねるとスキームを合算する。  
  スキームで分けると、端末のトークンが管理だけの API を通ってしまう
- 端末のトークンのリクエストは、本文やクエリの店舗・端末がトークンと一致することを検証する (違えば 403 `TERMINAL_MISMATCH`)
  - 検証する: 書き込み (シフト、入出金、精算、取引の登録と取消、受注の登録・入荷・キャンセル、前受金の受取と返金、在庫の変更、入荷と移動の受領) と、自端末のシフトの参照
  - 適用しない: 読み取り (他店の在庫など) と管理画面のリクエスト
- 管理画面は、管理者だけの操作のボタンを Operator には出さない。  
  対象はマスタの追加・編集・削除、会社設定の保存、商品の取込と画像、端末の登録、PIN の設定、締めの解除
- ユーザーの画面は管理者だけが開ける
- 担当と承認者は業務ルールとして検証する ([D-06](#d-06-値引とレジ係の取消は店長以上が承認する))

### D-37. 管理画面の自動更新はプロセス内の通知で行う

- Core の Service は、書き込みに成功した後に種類 (取引、シフト、在庫、受注、日次締め) を通知する
- ダッシュボードは通知を購読して再読み込みする。  
  管理画面 (Blazor Server) はサーバと同じプロセスにあるので、往復は要らない
- 受け付けなかった書き込み (重複、状態違い) は通知しない
- ダッシュボードは、続けて届く変更を 1 秒待ってまとめる。  
  端末の通信状態のために、1 分ごとにも再読み込みする
- 再読み込みするのはダッシュボードだけにする。  
  一覧のページは検索条件や選択を持つので、勝手に再読み込みすると操作を妨げる
- サーバは 1 台を前提にする (ほかのサーバの書き込みは通知が届かない)

### D-38. テレメトリとログは設定で出し分ける

- テレメトリは OpenTelemetry で出す
  - ログ・メトリクス・トレース: OTLP (`OTEL_EXPORTER_OTLP_ENDPOINT` があるとき)
  - メトリクス: Prometheus (`Prometheus:Uri`)
- 独自の計測 (稼働時間、API のリクエスト数と長時間の実行) は、API のグループのフィルターで取る
- SQL のログとトレースは、設定 (`Profiler`) で出す
- ログは Serilog にする
- HTTP のログと本文のダンプ (API だけ)、W3C のアクセスログは、設定 (`Log`) で切り替える
- 接続元のアドレスは、ログを書く時点の `HttpContext` から読んで全ログ行に付ける。  
  ミドルウェアの外側で書く行 (例外処理、HTTP のログ) にも付く
- W3C のアクセスログは例外処理の外に置き、未処理の例外も 500 で記録する
- HTTP のログは、本文を展開してから読むために圧縮の内側に置く
- API の未処理の例外は Problem Details で返す
- 画面のリクエストの未処理の例外は、エラーのページに出す
- 管理画面の回線の中の例外は、どれもログに記録する
  - ページの読み込み・書き込み: バナーに出す
  - ダイアログとそれ以外: `ErrorBoundary` が受けて [再試行] を出す

## 🔧 3. 開発

### D-39. モノレポにし、サーバと端末のソリューションを分ける

- 1 つのリポジトリに `server/Pos.Server.slnx` と `terminal/Pos.Terminal.slnx` を置く。  
  Visual Studio で個別に開いて動かす
- 共有の `shared/` は両方のソリューションに含める
- 共通のビルド設定 (`.editorconfig`、`Directory.Build.props` など) は、ルートに 1 組だけ置く
- 構成は [architecture.md §2](architecture.md#-2-プロジェクト構成)

### D-40. テストはプロジェクトごとに実行ファイルで動かす

- テストは xunit.v3 (Microsoft.Testing.Platform) の実行ファイルなので、テストプロジェクトごとに `dotnet run --project` で動かす。  
  `dotnet test` は使わない (`global.json` のオプトインが要らない)
- テストは次のプロジェクトに分ける
  - `Pos.Domain.Tests`: 計算と業務ルール
  - `Pos.Server.UnitTests`: 管理画面とサーバの部品
  - `Pos.Server.IntegrationTests`: 一時の DB で起動したサーバに API を呼ぶ
- Visual Studio のテストエクスプローラーからも実行できる

### D-41. 警告は 0 にし、抑止は理由のあるものだけにする

- サーバと端末は警告 0 でビルドし、InspectCode の指摘も 0 にする
- InspectCode はソリューション全体の解析をしない。  
  全体の解析は、テンプレートと同じにする端末の共通の部品のうち、POS で使わないメンバーを `.Global` の指摘で挙げる
- 抑止は、避けられない理由のあるものだけにする
  - アセンブリ単位: `GlobalSuppressions.cs`
  - 箇所だけ: `#pragma warning disable` と `restore`
- 抑止の例
  - `Pos.Contract` の URL の文字列 (CA1056)
  - `EnumTextConverter<T>` の static abstract の実装 (CA1000)
  - ハッシュの `byte[]` のプロパティ (CA1819)
- NuGet の脆弱性の警告は抑止せず、推移的な依存を直接ピンする

### D-42. サンプルの取引は API を呼ぶツールで作る

- 初期データはマスタ・会員・在庫だけにし、取引とシフトは入れない
- 他店の在庫の照会を見せるため、店舗は複数にする
- レポートとダッシュボードを確認するための取引は、`server/tools/Pos.Server.SampleData` が作る。  
  端末と同じ経路 (`Pos.Domain` で計算して `POST /transactions`) で作るので、サーバの検証と副作用 (在庫、ポイント、連番) をそのまま使える
- ツールは、管理画面のフォームで管理者としてログインする
- 有効な店舗 × 端末ごとに、直近の日数分の開設 → 販売 → 返品 → 取消 → 出金 → 精算を登録する。  
  前日までを締める
- 初日の在庫は、仕入先への発注から作った入荷予定を受領して積む
- 店舗ごとに、入荷待ちの発注を 1 件残す
- 乱数は `--seed` で固定し、同じ引数なら同じ内容になる (ID と時刻は除く)
- ツールは `Pos.Domain` と `Pos.Contract` だけを参照し、サーバの Core と Host には依存しない
